# 学员靶机修复操作说明

**适用对象：** 参加塔大网安师市行 CTF-AWD 实战训练的全体学员  
**版本：** v1.0（2026-11-03）  
**使用范围：** 仅限本次授权训练环境

> **核心原则：先恢复服务，再修补漏洞，最后验证。不要删除 Flag，不要清空数据卷，不要绕过平台直接操作宿主机。**

---

## 0. 一分钟速查

| 现象 | 优先处置 |
|---|---|
| 服务异常、连接被拒绝 | 进入终端检查进程和监听端口；修复后从平台重启 |
| 页面 502 / 500 | 检查应用进程、上游服务和错误日志 |
| 终端打不开 | 关闭终端重开、刷新页面；仍失败联系管理员 |
| 状态显示「恢复中」 | 等待平台自动恢复，不要连续点击重启 |
| 状态显示「待人工处理」 | 停止反复重启，立即联系管理员 |
| Flag 提交无效 | 确认是其他队伍当前轮次的 Flag，不要提交本队 Flag |
| 怀疑被植入后门 | 先隔离可疑文件，再修漏洞、换口令、重启验证 |

---

## 1. 登录与进入靶机

1. 使用管理员分配的账号登录平台。
2. 进入「我的靶机」（`/targets`）。
3. 每行代表本队的一个服务靶机，可查看：
   - 服务名称
   - 比赛入口（`服务器地址:公网端口`）
   - 容器名称
   - 当前状态
   - 最近检查时间
4. 点击「终端」，在弹出窗口中等待连接成功。
5. 终端只允许访问**本队管理网关**，不能访问其他队伍管理网或宿主机。

> 同一队伍的成员共用同一个服务靶机。你在终端里的修改会立即影响全队，修复前先在队内沟通，避免多人同时改同一文件。

---

## 2. 认识靶机状态

| 状态 | 含义 | 学员动作 |
|---|---|---|
| 已创建 | 靶机记录已创建，尚未启动 | 联系管理员确认是否需要初始化 |
| 启动中 | 容器正在启动 | 等待，不要重复操作 |
| 运行正常 | 健康检查通过 | 保持监控，继续防守 |
| 服务异常 | 健康检查失败 | 立即进入终端排查 |
| 恢复中 | 平台正在受控重启 | 等待恢复，不要连续重启 |
| 待人工处理 | 自动恢复次数已用完 | 联系管理员，附带排查信息 |
| 已停止 | 容器被停止 | 联系管理员确认原因 |

### 自动恢复规则

- 连续 **2 次**健康检查失败，平台会触发受控重启。
- **5 分钟内最多自动重启 2 次**。
- 仍无法恢复时，状态转为「待人工处理」。
- 服务状态本身不直接加减分，但服务不可用会影响队伍防守和 Flag 获取。

## 3. 标准修复流程

### 第一步：确认问题范围

先看「我的靶机」页面：

- 是单个服务异常，还是全部服务异常？
- 最近一次健康检查是什么时候？
- 状态是「服务异常」「恢复中」还是「待人工处理」？
- 比赛入口是否能连通？

不要一上来就重启。先判断是**进程挂了、端口没监听、应用报错、Flag 文件异常，还是平台侧网关问题**。

### 第二步：打开终端

点击对应服务的「终端」，等待状态变为「已连接」。

终端连接失败时：

1. 关闭终端窗口后重新打开；
2. 刷新「我的靶机」页面；
3. 检查本地网络和浏览器；
4. 仍失败则联系管理员，不要反复重启靶机。

### 第三步：最小化检查

进入终端后，先执行只读检查，不要急着删除文件：

```bash
# 当前身份和目录
id
pwd

# 查看进程
ps -ef

# 查看监听端口（没有 ss 时可用 netstat -lntp）
ss -lntp

# 检查本机服务是否响应，端口替换为服务实际内部端口
curl -i http://127.0.0.1:80/

# 检查磁盘和内存
df -h
free -m

# 查看 Flag 文件是否存在、权限是否正常
ls -l /data/flag
```

> Flag 路径由管理员在服务模板中配置，默认通常是 `/data/flag`。以本队实际配置为准，不要删除、覆盖或伪造 Flag 文件。

### 第四步：定位并修复漏洞

常见修复方向：

- **Web 服务**：检查 Web 根目录是否出现陌生文件、最近被修改的文件、可疑的 `eval`、`base64_decode`、命令执行代码。
- **应用进程**：查看应用日志，确认是否因配置错误、依赖缺失、数据库连接失败而崩溃。
- **权限问题**：确认应用用户能读取代码、写入必要目录、读取 Flag 文件。
- **弱口令**：修改应用后台、数据库、服务管理账号的弱口令。
- **后门与持久化**：检查异常进程、计划任务、启动脚本、SSH 公钥和陌生账号。
- **资源问题**：清理临时文件和无用日志，但不要删除 `/data` 数据卷。

可疑文件先**移动到隔离目录**，不要直接删除，便于回溯：

```bash
mkdir -p /tmp/quarantine
mv /path/to/suspicious-file /tmp/quarantine/
```

修复时注意：

- 不要执行 `reboot`、`shutdown` 或杀 PID 1；容器不会按你的预期重启。
- 不要运行 `docker`、`docker-compose` 等宿主机命令。
- 不要删除 `/data` 数据卷或 Flag 文件。
- 不要为了通过健康检查而伪造响应；平台会从攻击网络检查真实服务。

### 第五步：验证并重启

修复后先在终端内验证：

```bash
# 端口正常监听
ss -lntp

# 本机访问正常
curl -i http://127.0.0.1:80/

# Flag 文件存在且可读
ls -l /data/flag
```

确认无误后，回到「我的靶机」点击「重启」。

- 平台重启**保留数据卷和你的补丁**，不会重置镜像。
- 重启后等待状态恢复为「运行正常」。
- 终端会断开，需要重新打开。
- 不要在「恢复中」反复点击重启。

## 4. 常见故障处理

### 4.1 服务异常 / 连接被拒绝

**可能原因：**

- 应用进程崩溃
- 服务没有监听配置的内部端口
- 只监听了 `127.0.0.1`，没有监听 `0.0.0.0`
- 启动脚本或依赖损坏

**处理：**

1. `ps -ef` 查看进程；
2. `ss -lntp` 查看端口；
3. 查看应用错误日志；
4. 修复启动命令或配置；
5. 从平台重启并验证。

### 4.2 页面 502 / 500

- 502 通常是反向代理找不到上游服务：检查上游进程和端口。
- 500 通常是应用自身异常：检查应用日志和最近修改的代码。
- 不要只重启反向代理，要找到真正失败的服务。

### 4.3 服务显示正常，但页面被篡改

- 检查 Web 根目录最近修改的文件；
- 查找陌生脚本、跳转代码、外链和隐藏 iframe；
- 恢复正确页面；
- 修补导致文件被写入的漏洞；
- 修改相关账号口令；
- 重启后再次检查。

### 4.4 Flag 读取异常

- 确认 Flag 路径是否与管理员配置一致；
- 检查文件权限和应用运行用户；
- 确认应用每次请求都重新读取 Flag，而不是缓存旧值；
- 不要手动写入假 Flag；
- 如果 Flag 文件被删除，联系管理员处理，不要自行重建。

### 4.5 终端无法连接

1. 关闭终端重开；
2. 刷新页面；
3. 尝试其他浏览器或无痕窗口；
4. 检查本地网络；
5. 联系管理员，说明队伍、服务、时间和错误提示。

### 4.6 状态「待人工处理」

说明平台自动恢复已经达到上限。此时：

- 不要反复点击重启；
- 保留终端中的错误信息；
- 按第 8 节模板向管理员上报；
- 等待管理员处理后再继续修复。

## 5. 修复后的验证清单

- [ ] 服务进程存在且稳定运行
- [ ] 服务监听 `0.0.0.0:<内部端口>`
- [ ] 本机 `curl` 或端口探测正常
- [ ] Flag 文件存在且应用可读
- [ ] 页面/接口功能正常
- [ ] 没有陌生进程、计划任务、SSH 公钥
- [ ] 可疑文件已隔离，漏洞已修补
- [ ] 相关弱口令已修改
- [ ] 平台状态恢复为「运行正常」
- [ ] 队内已同步修改内容

---

## 6. 团队协作要求

- 每队 3—4 名成员共用同一套服务靶机。
- 建议分工：一人主攻、一人防守修补、一人监控状态与提交 Flag。
- 同一时间尽量只安排一人修改靶机，避免互相覆盖。
- 修改前在队内说明改哪个服务、哪个文件、预计多久。
- 修复完成后由另一名成员复核，不要只依赖一个人的判断。
- 不要把本队 Flag、终端口令或修复脚本发到队伍之外。

---

## 7. 比赛纪律与安全边界

- 只能攻击其他队伍**已开放的比赛端口**。
- 禁止访问宿主机管理接口、云元数据地址、其他队伍管理网。
- 禁止 DoS/DDoS、批量删除、勒索、破坏平台服务。
- 禁止删除或伪造 Flag、篡改计分数据。
- 禁止在靶机中植入影响平台运行的持久化后门。
- 所有终端操作和关键动作会按平台审计策略记录。
- 如对操作边界有疑问，先询问现场管理员。

## 8. 上报模板

无法自行恢复时，按以下格式联系管理员：

```text
队伍：第 __ 队
服务：____________
容器：____________
时间：____________
当前状态：服务异常 / 恢复中 / 待人工处理 / 终端无法连接
现象：________________________________________________
已做操作：____________________________________________
终端报错（如有）：____________________________________
需要支持：____________________________________________
```

附带信息越完整，处理越快。不要只发“靶机坏了”。

## 10. 重要提醒

1. **平台重启不是重置。** 重启保留数据卷和补丁，适合修复后恢复服务。
2. **不要删除 `/data`。** 数据卷里可能有服务数据和 Flag。
3. **不要伪造 Flag。** 平台按轮次注入并校验，伪造无效。
4. **不要绕过平台操作宿主机。** 终端只用于本队服务修复。
5. **先修漏洞，再重启。** 只重启不修漏洞，很快会再次被打穿。
6. **队内共享靶机。** 任何修改都会影响全队，操作前先沟通。
