# 管理员操作手册

塔大网安师市行 CTF-AWD 实战平台 · 管理员端

## 1. 部署与首次登录

一键部署（详见仓库 README）：

```bash
git clone https://github.com/gengarbypass/ctf-awd-platform.git
sudo bash ctf-awd-platform/deploy.sh
```

- 初始管理员账号 `admin`，密码在部署脚本输出中打印并保存在 `deploy/.env`。**首次登录后请立即在「选手管理」中重置为强密码。**
- 管理端与选手端同域名，admin 账号登录后自动进入 `/admin`。

日常运维：

```bash
docker compose -f deploy/docker-compose.yml ps          # 状态
docker compose -f deploy/docker-compose.yml logs -f api worker
docker compose -f deploy/docker-compose.yml restart api worker terminal
bash scripts/backup.sh                                   # 数据库备份（需 PG 环境变量）
```

## 2. 赛前准备清单

按顺序完成：

1. **创建队伍**（/admin/teams）：编号 1—15、名称唯一；初始分自动 1000；邀请码字段保留兼容，不开放自助注册。
2. **创建选手**（/admin/users）：选手必须归属队伍且每队限 3—4 人；由管理员创建账号并分配初始密码。管理员账号不挂队伍。
3. **配置服务模板**（/admin/services）：首次部署服务模板为空，逐项填写服务代码、编号、内部端口、Flag 路径和镜像；镜像必须能从服务器拉取，保存后可点「预检镜像」验证。每队每种服务会创建一个靶机实例。
4. **创建比赛**（/admin/match）：设置名称、开始/结束时间（默认时长 4 小时）、轮换周期（默认 300 秒，可 180—600）与宽限（默认 30 秒）。
5. **初始化靶机**（/admin/targets →「初始化缺失靶机」）：按队伍×服务模板幂等创建容器、独立数据卷、管理网关与端口映射，重复执行不会重置已有实例或成绩。
6. **赛前检查**（/admin/match →「完成赛前检查」）：全部靶机健康后比赛从草稿变为待开始；有问题会指出具体队伍和服务。
7. **核对分数**：确认所有队伍均为 1000 分。
8. **开始比赛**：选手每队满 3—4 人才能开赛；未到计划开始时间会自动顺延。

## 3. 比赛控制（/admin/match）

- **开始 / 暂停 / 恢复 / 结束**：暂停会同步停止计时、Flag 轮换和提交（页面、终端、状态查看保留）；恢复自动顺延结束时间；结束后不可恢复。
- **冻结计分板**：冻结期间前台展示冻结时刻快照，后台继续验判计分并保存流水，解除后展示最新结果。用于赛前封榜或收尾阶段。
- 顶部状态条展示五态流转（草稿 → 待开始 → 进行中 ⇄ 已暂停 → 已结束），当前态高亮。
- 草稿态可修改时间与轮换参数；开赛后锁定，正式运行中修改计分参数需重新初始化比赛。

## 4. 运行总览（/admin）

一屏掌握：比赛状态与当前轮次、在线队伍/选手数、正常靶机比例、异常靶机列表（优先处理「待人工处理」）、最新提交流。有效攻击后计分板最迟 5 秒更新。

## 5. 靶机管理（/admin/targets）

- 按队伍、状态筛选；支持**重启**（保留数据卷）、**启动/停止**、**健康记录**（历史检查时间、耗时、错误）。
- 自动恢复规则：连续两次失败 → 受控重启（保留选手补丁）→ 连续两次成功恢复运行；5 分钟内最多自动重启 2 次，超过转「待人工处理」并告警。
- 手动处置路径：查看健康记录定位原因 → 终端进入容器修复 → 重启验证；需要整队重置镜像时务必先确认（会清选手补丁）并说明原因，操作全部入审计。

## 6. 提交与流水（/admin/submissions）

- 两个页签：全部 Flag 提交（验判结果、双方分数变化、请求 ID）与计分流水（核算依据，可按队伍核对）。
- **人工改分**：必须选择队伍、填写非零分值和原因；系统保存修改前后分数、操作人并写入独立流水与审计。
- **导出成绩**：CSV 含队伍汇总（TEAM）与全部流水（LEDGER），用于赛后归档与重算校验（`总分 = 1000 + Σ攻击 − Σ被攻击`）。

## 7. 公告管理（/admin/announcements）

发布（通知/注意/重要三级）、置顶、撤回；发布后实时推送到在线选手页面。服务异常、时间调整、纪律提醒都应发公告留痕。

## 8. 审计日志（/admin/audit）

记录认证、队伍、用户、比赛、靶机、公告、人工改分与终端连接等关键操作（操作人、对象、详情、请求 ID）。Flag 日志仅存哈希。可按对象类型筛选、按操作人/动作/请求 ID 搜索。

## 9. 安全与边界要求

- 选手只能管理本队靶机；跨队仅开放比赛端口（`20000 + 队伍号 × 100 + 服务号`）。
- PostgreSQL/Redis/API/Worker/Docker 接口不对公网暴露；容器非特权运行并限制 CPU/内存/进程数。
- 云资源操作走 RAM 用户/角色，服务器不保存主账号 AccessKey。
- 阿里云安全组：443/80 对全网，22 限管理员 IP，比赛端口段按实际队伍数开放。
- 数据库比赛期间每 5 分钟备份（`systemd/awd-backup.timer`），OSS 开版本控制；恢复演练按「暂停比赛 → 恢复数据库 → 校验分数与流水 → 重启服务 → 恢复比赛」顺序执行。

## 10. 故障处置速查

| 现象 | 处置 |
|---|---|
| 单靶机异常 | 靶机管理看重启次数，≤2 等自动恢复；转人工后终端进容器修复 |
| Flag 轮换失败告警 | 总览/日志定位靶机，轮换失败不影响其他队伍；修复后下轮自动重试 |
| 计分板不动 | 先看事件与 API 日志；必要时 `docker compose restart api` |
| 选手无法登录 | 检查账号是否被禁用、队伍是否满员；重置密码在选手管理 |
| 需要回滚数据 | `CONFIRM_RESTORE=yes bash scripts/restore.sh <备份文件>`（先暂停比赛并停 API/Worker） |
